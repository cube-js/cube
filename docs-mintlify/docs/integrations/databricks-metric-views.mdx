Cube publishes selected, deployed Cube views as native Metric Views in your Databricks Unity
Catalog. Databricks applications query those objects directly; they do not query Cube at runtime.
Your Cube model remains the source of truth. Publication is **one-way**: it does not import
Databricks definitions into Cube. You start it from Console or the public REST API, or have Cube
[publish after each deployment](#publish-after-each-deployment).

## Before you start

- Configure a [Databricks data source](/admin/connect-to-data/data-sources/databricks-jdbc)
  and deploy a YAML data model with public views. This workflow reads the latest successful
  deployed build, not unsaved IDE changes. If
  [`driver_factory`](/reference/configuration/config#driver_factory) in `cube.py` serves the
  data source instead of environment variables, see
  [Data sources served by `driver_factory`](#data-sources-served-by-driver_factory).
- If a Cube source uses a two-part `schema.table` name, set
  [`CUBEJS_DB_DATABRICKS_CATALOG`](/reference/configuration/environment-variables#cubejs_db_databricks_catalog)
  for that data source so Preview can resolve its catalog, or the **Default catalog** of a
  [publication target with its own connection](#publish-to-another-workspace). Without it, those
  views are blocked.
- Ask your Databricks administrator for a **dedicated target catalog and schema** for the
  published Metric Views.
  The Databricks identity Cube publishes with (the data source's, or a publication target's own
  service principal) needs `CAN USE` on its SQL warehouse,
  `USE CATALOG` and `USE SCHEMA` on the target and source namespaces, `SELECT` on source
  relations, and `CREATE TABLE` on the target schema. The same identity must own any existing
  Cube-managed Metric View it needs to update. It owns the temporary views it creates for the
  access test. See the [Databricks Metric View prerequisites](https://docs.databricks.com/aws/en/uc-semantics/metric-views/create)
  and [Metric View ownership guidance](https://docs.databricks.com/aws/en/uc-semantics/metric-views/manage)
  (AWS documentation; use the equivalent pages for Azure or Google Cloud).
- Arrange target access for Databricks consumers separately. Publishing an object does not
  grant them `SELECT` on it or access to its catalog and schema.
- Databricks evaluates access to the published object under Unity Catalog permissions, not
  Cube's query-time authorization. A view with a Cube access policy, or one that references a cube
  with an access policy, is blocked from publication; Cube access policies are never transferred
  to Databricks. Review the **Preview** result and configure Databricks grants before exposing a
  target to consumers.
- Cube uses Databricks credentials only server-side. Preview returns generated YAML to authorized
  users for review.

## Publish a view

The full publication flow requires `SchemaUpdate`
[deployment access](/admin/users-and-permissions/custom-roles). `SchemaRead` is enough to run and
inspect Preview, but not to save settings, test access, or sync. A data model with Jinja templates
also needs **Access SQL Runner** (`SqlRunnerRead`); see [Jinja templates](#jinja-templates).

<Steps>
  <Step title="Configure publication">
    Open your deployment's **Settings → Data Sources** and edit the Databricks data source.
    Expand **Databricks Metric View sync**. Enter the target catalog and schema. Choose all
    views, selected views, or a name pattern; optionally add a target-name prefix. Choose what
    happens when a view leaves the scope (see [Removed views](#removed-views)). Turn publication
    on and save. This alone does not start a write.
  </Step>
  <Step title="Preview the deployed model">
    Run **Preview**. Inspect every view's generated YAML, source relation, warnings, and blocking
    issues. It reads the deployed model and **does not write to Databricks**. Preview payloads and
    results are retained for at most seven days; run it again if an older result is gone.
  </Step>
  <Step title="Test access">
    With a completed preview selected, run **Test access**. It checks source reads as well as
    warehouse, target-schema, and temporary create/replace/drop access. The test creates and
    cleans up a uniquely named temporary view; it does not change a final target.
  </Step>
  <Step title="Publish and inspect each result">
    Select **Publish now**. Review the result for **each view** in run history. **Created**,
    **Updated**, and **Unchanged** are successful outcomes; **Blocked**, **Rejected by Databricks**,
    and **Write failed** need investigation. A run is **Partial** if some views succeeded and others
    did not, or if a drop of an obsolete Metric View was held or failed (see
    [Removed views](#removed-views)); if no view succeeded, it is **Failed**. A view that
    Databricks rejected or failed to write can also show Databricks' error class, such as
    `UNRESOLVED_COLUMN.WITH_SUGGESTION`, and a **Statement ID**. Look up that statement in
    Databricks Query History to see the full error.
  </Step>
</Steps>

Preview and sync each resolve the latest successful deployed build when started. If a new build
lands between them, preview again before syncing. To test Metric Views in a staging catalog and
then publish that same build to production, see
[Publish to staging, then production](#publish-to-staging-then-production) or the
[Cube CLI](/reference/cli#databricks-metric-views).

Scope rules:

- The name pattern supports literals, `^`, `$`, a bare `.` that matches any single character, and
  at most one `.*` wildcard. It is not a general regular expression and is limited to 128
  characters. Review the matched views in Preview before syncing.
- **All views** (`all` in the API) takes every view in the deployed YAML model, including
  views with `public: false` and views over another data source's cubes. Preview and sync block
  the latter with `CUBE_DATA_SOURCE_MISMATCH`, so when the model has such views, every **all** run
  ends **Partial** or **Failed**, which the [CI recipe](#trigger-publication-from-ci) and
  [promotion](#publish-to-staging-then-production) don't accept. Scope such a data source with
  **selected** or **pattern** instead.
- Each preview or sync resolves at most 128 views, whether the scope is **all**, **selected**, or
  **pattern**. **all** and **pattern** count the views of every data source in the model; if they
  resolve more, preview and sync reject the request. Narrow the scope and try again.
- A newly deployed view enters an **all** or matching **pattern** scope on the next sync: the
  deployment's own run when you [publish after each deployment](#publish-after-each-deployment).
  A **selected** scope changes only when you edit it.
- A selected view you remove from the data model or rename stays selected: preview and sync block
  it with `CUBE_VIEW_NOT_FOUND`, every run ends **Partial** or **Failed**, and its Metric View is
  never dropped. Deselect it.
- Renaming a view or target creates a new target. The old one is kept, or dropped under
  **Delete the Metric View Cube created** (see [Removed views](#removed-views)).
- Per-view target-name and root-source overrides are available through the configuration API,
  but are not editable in the card.

The public REST API documents [reading settings](/api-reference/databricks-metric-view-integration/get-databricks-metric-view-publication-settings),
[saving settings](/api-reference/databricks-metric-view-integration/create-or-update-databricks-metric-view-publication-settings),
[starting a preview](/api-reference/databricks-metric-view-publication/start-a-databricks-metric-view-publication-preview),
[checking preview status](/api-reference/databricks-metric-view-publication/get-databricks-metric-view-preview-status),
[getting the completed preview result](/api-reference/databricks-metric-view-publication/get-a-completed-databricks-metric-view-preview-result),
and [cancelling a preview](/api-reference/databricks-metric-view-publication/cancel-a-databricks-metric-view-preview).
The same API supports [starting a publication run](/api-reference/databricks-metric-view-integration/start-a-databricks-metric-view-publication-run),
[inspecting a run](/api-reference/databricks-metric-view-integration/get-a-databricks-metric-view-publication-run),
[listing runs](/api-reference/databricks-metric-view-integration/list-databricks-metric-view-publication-runs),
and [cancelling a run](/api-reference/databricks-metric-view-integration/cancel-a-databricks-metric-view-publication-run).
Contact [Cube support](/admin/account-billing/support) for help with access.

When saving settings through the API, `deletionPolicy` is `retain`, the default, or
`delete-managed`, which drops obsolete Metric Views as [Removed views](#removed-views) describes.
A save that omits it stores `retain`, even when `delete-managed` was stored before.

## Data sources served by `driver_factory` {#data-sources-served-by-driver_factory}

Publication can't use a connection that
[`driver_factory`](/reference/configuration/config#driver_factory) creates: Preview, Test access,
and sync run without a user for the factory to act for. So every
[publication target](#publish-to-staging-then-production) of such a data source needs a Databricks
service principal connection of its own: the card requires its fields, with no
**Use a separate connection** switch. Your users' queries keep going through `driver_factory`.

<Warning>

Don't give the data source a service principal with **+ Add data source** or **Edit**. The
Databricks driver prefers a data source's OAuth client variables over the per-user `token` that
`driver_factory` returns, so every query on it would run as the service principal. See
[Data sources served by `driver_factory`](/admin/connect-to-data/multiple-data-sources#data-sources-served-by-driver_factory).

</Warning>

1. In Databricks, create a
   [service principal with an OAuth secret](https://docs.databricks.com/aws/en/dev-tools/auth/oauth-m2m)
   and grant it the privileges listed in [Before you start](#before-you-start).
2. In **Settings → Data Sources**, select **Set up Metric View sync for a cube.py data source**.
   Enter the data source name your cubes set in `data_source` (`default` for cubes that set none)
   and select **Continue**.
3. In **Databricks Metric View sync**, under **Databricks connection**, enter the SQL warehouse's
   **Server hostname** and **HTTP path** and the service principal's **OAuth client ID** and
   **OAuth client secret**. If a cube uses a two-part `schema.table` name, also enter the
   **Default catalog** it resolves in; it replaces `CUBEJS_DB_DATABRICKS_CATALOG` for this
   publication target.
4. Configure and run publication as in [Publish a view](#publish-a-view). Preview is available
   once the credential is saved.

Cube stores the secret encrypted and never returns it. To rotate it, enter a new secret and save;
changing the hostname or client ID also requires the secret again. A data source whose
environment variables configure another driver can't take a credential until you remove them.

Through the API, pass the credential as `connection` (`host`, `httpPath`, `clientId`,
`clientSecret`, and an optional `catalog`) when
[saving settings](/api-reference/databricks-metric-view-integration/create-or-update-databricks-metric-view-publication-settings).
Omit it to keep the stored credential, or pass `null` to remove it.

## Publish after each deployment {#publish-after-each-deployment}

Cube can publish every time a build of the deployment succeeds, so Databricks follows your Cube
model without a manual sync or a CI step. Set up publication as in [Publish a view](#publish-a-view),
including **Preview**, **Test access**, and a first sync. Then turn on **Publish after each
deployment** in the **Databricks Metric View sync** card and save. Through the API, save
`syncOnDeploy: true`. The setting is off by default, and a save that omits it turns it off.

After each successful build, Cube starts a run for every Databricks data source of the deployment,
and for every [publication target](#publish-to-staging-then-production) of such a data source, that
has publication and this setting turned on. Changes in development mode publish nothing until they
are deployed. Each run:

- Converts the build that just succeeded, with the saved settings: scope, target, and what happens
  when a view leaves the scope. Under **Delete the Metric View Cube created**, a deployment that
  removes a view drops its Metric View (see [Removed views](#removed-views)).
- Runs as the user who deployed. A build started by a Git push has no user, so the run uses
  whoever last saved the settings. For a data model with [Jinja templates](#jinja-templates), that
  user needs **Access SQL Runner**, or the build is not published.
- Shows **Deployment** under **Triggered by** in run history (`trigger: DEPLOYMENT` in the API).
  Runs you start from the card or the API show **Manual** (`MANUAL`).
- Starts the SQL warehouse if it's stopped, as every sync does, even for a build that changes no
  view.

If another run is active, or the deployment is still rolling out a build with Jinja templates,
the run retries for about 30 minutes. If a newer build succeeds first, only the newer build
publishes.

A run that can't start leaves no entry in run history. This happens when no user can render the
model's Jinja templates, when the publication target has no Databricks connection to use, or when
the retry runs out. Databricks then keeps the Metric Views of an earlier build, and the card
[warns that Databricks is behind](#databricks-behind-the-deployed-model).

A run that completes sends no notification. A run that fails, ends **Partial**, or withholds a
measure notifies its user in the [Inbox](/docs/inbox).

## Trigger publication from CI

The [Cube CLI](/reference/cli#databricks-metric-views) can start a run and wait for it with
`cube dbx-mv sync --wait`, and publish a tested staging build to production. Unlike the recipe
below, it doesn't retry a start refused with `409`, and it checks only that the run is `COMPLETED`
with an `incompleteViewCount` of 0.

Run publication from CI after a successful Cube deployment when CI should check the result. To
just publish after each deployment, [turn on the setting](#publish-after-each-deployment) instead;
don't do both for one publication target, or each build starts two runs there. First, configure
the scope (see the scope rules under [Publish a view](#publish-a-view)), a dedicated target catalog
and schema, and publication enabled in **Settings → Data Sources**. With
**When a view leaves the scope** set to **Delete the Metric View Cube created**, each CI run also
drops the Metric Views the deployment made obsolete (see [Removed views](#removed-views)). Run
**Preview** and **Test access** before the first write. CI uses these saved settings; the API call
does not override the scope or destination.
For a [publication target](#publish-to-staging-then-production) other than `default`, pick it under
**Publication target** in the card first.

Store a [Platform API key](/api-reference/authentication) with deployment `SchemaUpdate` access as
a CI secret. The recipe reads the saved settings, starts a run with their `configurationVersion`,
then polls the returned `statusUrl`. The start endpoint returns `202` with a `runId`, `buildJobId`,
optional `commit`, root-relative `statusUrl`, and `reused`. It accepts an optional UUID
`idempotencyKey` for safe retries: a repeated key returns the earlier run with `reused: true`, but
`buildJobId` and `commit` name the build this request resolved, not the reused run's. The run's
status response carries the run's own `buildJobId`, which the recipe checks. A start returns `409`
while another run of that publication target is active,
while a [take-over](#take-over-an-existing-metric-view) runs in your account, and, for a data model
with [Jinja templates](#jinja-templates), while the deployment is still rolling out the new build.
The recipe retries a `409` for up to `MAX_START_ATTEMPTS` attempts, 10 seconds apart (default: 30).
A stale `configurationVersion` also returns `409` ("The integration changed after it was loaded");
retrying can't clear it, so the recipe stops. Run it again to read the saved settings.
Run statuses are `QUEUED`, `RUNNING`, `CANCELLING`, `COMPLETED`, `PARTIAL`, `FAILED`, and `CANCELLED`.

To reject incompatible changes before writing, CI can [preview](/api-reference/databricks-metric-view-publication/start-a-databricks-metric-view-publication-preview)
with the saved scope and any saved `sourceOverrides`, such as
`{"dataSourceName": "default", "selectionMode": "all"}` (or `selected` with `viewNames`, or
`pattern` with `viewNameRegex`), plus `"target": "<name>"` for a
[publication target](#publish-to-staging-then-production) other than `default`, and
[inspect the result](/api-reference/databricks-metric-view-publication/get-a-completed-databricks-metric-view-preview-result).
Require eligible views with no `withheldMembers`; avoid overlapping deployments because preview
and sync can resolve different builds.

This Bash step requires `curl` and `jq`. Set `CUBE_API_URL` to your tenant host without a trailing
slash, `DEPLOYMENT_ID` to the deployment that just succeeded, and `CUBE_API_TOKEN` to the CI secret.
Set `EXPECTED_BUILD_JOB_ID` if the deployment step returns one. The example uses the `default`
data source; URL-encode a different name in the path. For a
[publication target](#publish-to-staging-then-production) other than `default`, request
`"$integration?target=<name>"` for the settings and `"$integration/syncs?target=<name>"` to start
the run; the status poll needs no change. Set `SYNC_IDEMPOTENCY_KEY` to a UUID unique to this CI
publication attempt and keep it unchanged across retries of that attempt. Do not reuse it for a
later pipeline run: the API would return the earlier run without publishing again. Set `MAX_POLLS`
to scale the wait for your view count and warehouse start-up time (default: 180 attempts, 10
seconds apart, plus request time).

```bash
set -euo pipefail

integration="$CUBE_API_URL/api/v1/deployments/$DEPLOYMENT_ID/databricks-metric-view-integrations/default"
auth_header="Authorization: Bearer $CUBE_API_TOKEN"
: "${SYNC_IDEMPOTENCY_KEY:?Set a unique UUID for this publication attempt}"
settings=$(curl --fail --silent --show-error --connect-timeout 10 --max-time 30 \
  -H "$auth_header" "$integration")
if ! jq -e '.configuration.enabled == true' <<<"$settings" >/dev/null; then
  echo 'Enable publication before running CI.' >&2
  exit 1
fi
version=$(jq -r '.configurationVersion' <<<"$settings")

request=$(jq -n --argjson version "$version" --arg key "$SYNC_IDEMPOTENCY_KEY" \
  '{configurationVersion: $version, idempotencyKey: $key}')
max_start_attempts=${MAX_START_ATTEMPTS:-30}
[[ "$max_start_attempts" =~ ^[1-9][0-9]*$ ]] || { echo 'MAX_START_ATTEMPTS must be a positive integer.' >&2; exit 1; }
for ((attempt=1; ; attempt++)); do
  response=$(curl --silent --show-error --connect-timeout 10 --max-time 30 \
    --write-out '\n%{http_code}' -X POST -H "$auth_header" \
    -H 'Content-Type: application/json' --data-binary "$request" "$integration/syncs") || response=$'\n000'
  http_code=${response##*$'\n'}
  start=${response%$'\n'*}
  [[ "$http_code" == 202 ]] && break
  echo "Starting the run returned HTTP $http_code: $start" >&2
  [[ "$http_code" == 409 && "$start" != *'changed after it was loaded'* ]] &&
    ((attempt < max_start_attempts)) || exit 1
  sleep 10
done
status_url=$(jq -r '.statusUrl' <<<"$start")

max_polls=${MAX_POLLS:-180}
[[ "$max_polls" =~ ^[1-9][0-9]*$ ]] || { echo 'MAX_POLLS must be a positive integer.' >&2; exit 1; }
for ((attempt=0; attempt<max_polls; attempt++)); do
  run=''
  response=$(curl --silent --show-error --connect-timeout 10 --max-time 30 \
    --write-out '\n%{http_code}' \
    -H "$auth_header" "$CUBE_API_URL$status_url") || response=$'\n000'
  http_code=${response##*$'\n'}
  case "$http_code" in
    200) run=${response%$'\n'*} ;;
    000|429|5??)
      echo "Status poll returned HTTP $http_code; retrying $CUBE_API_URL$status_url" >&2
      sleep 10
      continue ;;
    *) echo "Status poll returned HTTP $http_code: $CUBE_API_URL$status_url" >&2; exit 1 ;;
  esac
  if [[ -n "${EXPECTED_BUILD_JOB_ID:-}" ]] &&
    ! jq -e --argjson expected "$EXPECTED_BUILD_JOB_ID" '.buildJobId == $expected' <<<"$run" >/dev/null; then
    jq '{runId, buildJobId, commit}' <<<"$run" >&2
    echo "Run started against a different build; inspect or cancel it before retrying: $CUBE_API_URL$status_url" >&2
    exit 1
  fi
  case "$(jq -r '.status' <<<"$run")" in
    QUEUED|RUNNING|CANCELLING) sleep 10 ;;
    *) break ;;
  esac
done

if [[ -z "$run" ]]; then
  echo "Last status poll returned HTTP $http_code after $max_polls attempts: $CUBE_API_URL$status_url" >&2
  exit 1
fi
case "$(jq -r '.status' <<<"$run")" in
  QUEUED|RUNNING|CANCELLING)
    echo "No terminal run status observed after $max_polls attempts: $CUBE_API_URL$status_url" >&2
    exit 1 ;;
esac

if ! jq -e '.status == "COMPLETED" and .incompleteViewCount == 0 and
  (.viewNames | length > 0) and
  (.views | length > 0) and
  all(.views[]; .outcome == "created" or .outcome == "updated" or
    .outcome == "unchanged" or .outcome == "deleted_obsolete" or
    (.outcome == "retained_obsolete" and .detail == null))' \
  <<<"$run" >/dev/null; then
  jq '{status, buildJobId, commit, incompleteViewCount, viewNames, views}' <<<"$run" >&2
  exit 1
fi
```

The expected-build check runs **after** publication starts; a mismatch cannot prevent or undo a
write. `viewNames` lists planned views; `retained_obsolete` means an obsolete target was left in
place, and `deleted_obsolete` that Cube dropped it. A `retained_obsolete` target with a `detail` is
a drop that was held or failed, so the recipe rejects it. A hold that repeats keeps CI failing
until you clear it: for `deletion-cap-exceeded`, restore views or revert the target-name change as
[Removed views](#removed-views) describes; drop a `precondition-failed` Metric View in Databricks
yourself; or switch **When a view leaves the scope** to **Keep its Metric View in Databricks**,
which reports obsolete targets without a `detail`. Publication-run `views[].outcome` values are
`unchanged`, `created`, `updated`, `blocked`, `validation_failed`, `publish_failed`,
`retained_obsolete`, and `deleted_obsolete`; these differ from preview outcomes. The recipe
accepts only the successful outcomes. A `validation_failed` or `publish_failed` view carries
`errorClass`, Databricks' error class such as `UNRESOLVED_COLUMN.WITH_SUGGESTION`, and
`statementId`, the Databricks statement the failed publish ended on. Each is `null` when Databricks
named no error class or no statement ran, and both are `null` in older runs. Cube does not return
Databricks' error message; look up the statement in Databricks Query History to read it. Such a
view's `detail` is a failure code such as `STATEMENT_FAILED`. On a `publish_failed` view,
`AUTHENTICATION_FAILED`, `PERMISSION_DENIED`, `WAREHOUSE_UNAVAILABLE`, or `TIMEOUT` means Cube
couldn't use Databricks, not that Databricks rejected the definition.
Each `views[]` entry carries its destination as `target` (`catalog.schema.name`, or `null` when
conversion blocked the view), and a run carries the `takeOverTargets` it was started with. A
`blocked` view whose `detail` is `conversion-blocked` didn't convert: Preview lists its issues. One
whose `detail` is
`unmanaged-target` or `ownership-conflict` collides with an object this publication target does
not manage, and a `detail` of `taken-over` marks a view a take-over published. After you confirm
that a blocked destination should belong to this publication target, a CI job can pass its
`target` in `takeOverTargets` to
[take it over](#take-over-an-existing-metric-view). A `detail` of `metastore-changed` means the
data source [moved to another metastore](#move-to-another-metastore) during the run; start
another run.
`incompleteViewCount` counts `created`, `updated`, and `unchanged` views whose `withheldMembers`
list is nonempty; requiring zero rejects definitions missing measures.

Failed checks do not roll back writes. Inspect `views[]` for errors or `withheldMembers`. List
older runs with
`GET /api/v1/deployments/{deploymentId}/databricks-metric-view-integrations/{dataSourceName}/syncs`
and request cancellation of an active run with `DELETE {statusUrl}`. Cancellation stops further
writes but does not undo completed ones. `curl --fail` exits with code 22 and omits the response
body on HTTP errors.

## Publish to staging, then production {#publish-to-staging-then-production}

A data source can have several publication targets, such as `staging` and `production`. Each has
its own settings (target catalog and schema, scope, target-name overrides, `deletionPolicy`,
`syncOnDeploy`, and a [Databricks connection](#publish-to-another-workspace) of its own, if any),
its own run history, and its own Metric Views. What this page says about a data source's settings,
runs, and Metric Views holds for each publication target. Give each one its own catalog or schema:
a Metric View belongs to one publication target, so another that publishes to the same name is
blocked with `ownership-conflict`.

The card always lists the `default` publication target, but it exists only once its settings are
saved; until then, reading its settings or starting a run returns `404`. In the
**Databricks Metric View sync** card, pick one under
**Publication target**: the settings, **Preview**, **Test access**, and run history below it are
that target's own. To create one, select **Add target**, enter its name, then save its
settings. Through the API, add `?target=<name>` when
[reading settings](/api-reference/databricks-metric-view-integration/get-databricks-metric-view-publication-settings),
[saving settings](/api-reference/databricks-metric-view-integration/create-or-update-databricks-metric-view-publication-settings),
[starting a run](/api-reference/databricks-metric-view-integration/start-a-databricks-metric-view-publication-run),
or [listing runs](/api-reference/databricks-metric-view-integration/list-databricks-metric-view-publication-runs),
and pass `target` in a [preview](/api-reference/databricks-metric-view-publication/start-a-databricks-metric-view-publication-preview)
request body. Without it, a request uses `default`. Reading or cancelling a run by its `runId`
needs no `target`.

- **Names:** a name starts with a letter and has up to 63 letters, digits, `_`, and `-`; Cube
  lower-cases it.
- **Creating:** through the API, only saving with `expectedConfigurationVersion: 0` creates a
  publication target, `default` included, so a misspelled name there creates a new one. Reading
  settings, starting or listing runs, or previewing with a name that doesn't exist returns `404`.
- **Listing:**
  `GET /api/v1/deployments/{deploymentId}/databricks-metric-view-integrations/{dataSourceName}/targets`
  returns every saved publication target of the data source, sorted by name (`404` if none): its
  `targetName`, `enabled`, `syncOnDeploy`, `targetCatalog`, `targetSchema`, `configurationVersion`,
  and `lastRun` (its newest run's `runId` and `status`, or `null` if it never ran). Use it to find
  one created by a misspelled name.
- **Turning off:** saving `enabled: false` drops nothing, and the publication target keeps its
  Metric Views: another that publishes to the same names is blocked with `ownership-conflict`
  until it [takes them over](#take-over-an-existing-metric-view).
- **Deleting:** turn off **Publish to Databricks** and save, then select **Delete target**, or send
  `DELETE /api/v1/deployments/{deploymentId}/databricks-metric-view-integrations/{dataSourceName}?target=<name>&expectedConfigurationVersion=<n>`.
  `default` can't be deleted (`400`), and an unknown name returns `404`. A delete returns `409`
  while the target is enabled, while it has an active run or one that ended `CANCELLED` or `FAILED`
  in the last 10 minutes, or when the version is stale. The deleted target's Metric Views stay in
  Databricks, managed by no publication target, and the card lists them, as does the response's
  `retainedMetricViews`: drop them, or name them in another target's `takeOverTargets` before it
  publishes there. The deleted target's runs stay readable by `runId` and keep their `targetName`,
  but can't be promoted from. Its name can be used for a new publication target.

To publish to production the build you tested in staging:

1. Create `staging` and `production` with **Add target**, each with its own catalog or schema and
   **Publish to Databricks** on, and run **Test access** for each. Through the API, save each with
   `?target=<name>`, `expectedConfigurationVersion: 0`, and `enabled: true`. Leave
   `syncOnDeploy` off for production, so that no deployment publishes there untested.
2. Publish to staging: turn on [Publish after each deployment](#publish-after-each-deployment)
   for it with `syncOnDeploy: true`, or start its runs yourself.
3. Once a staging run is **Completed**, run your own checks against the staging Metric Views. Cube
   doesn't know whether they passed.
4. Promote the staging run: in staging's run history, select **Promote run to…** on that run,
   choose `production`, and confirm, which switches the card to production. The menu lists only
   the other publication targets with **Publish to Databricks** on.

   <Frame>
     <img
       src="https://static.cube.dev/docs/integrations/databricks-metric-views/promote-run-v2.png"
       alt="Run history of the staging publication target with a completed run expanded and its Promote run to… menu open, listing production"
     />
   </Frame>

   Through the API, start a production run with production's `configurationVersion` and
   `promoteFromRunId` set to the staging run's `runId`, here `STAGING_RUN_ID`. Set
   `PROMOTION_IDEMPOTENCY_KEY` to a UUID unique to this promotion, so that retrying the step
   doesn't start a second run:

```bash
set -euo pipefail

integration="$CUBE_API_URL/api/v1/deployments/$DEPLOYMENT_ID/databricks-metric-view-integrations/default"
auth_header="Authorization: Bearer $CUBE_API_TOKEN"
version=$(curl --fail --silent --show-error -H "$auth_header" \
  "$integration?target=production" | jq -r '.configurationVersion')
request=$(jq -n --argjson version "$version" --arg source "$STAGING_RUN_ID" \
  --arg key "$PROMOTION_IDEMPOTENCY_KEY" \
  '{configurationVersion: $version, promoteFromRunId: $source, idempotencyKey: $key}')
curl --fail-with-body -X POST -H "$auth_header" -H 'Content-Type: application/json' \
  --data-binary "$request" "$integration/syncs?target=production"
```

The request returns once the run starts: poll its `statusUrl` and check the result as the
[CI recipe](#trigger-publication-from-ci) does. The promoted run converts the staging run's build
with production's settings. Starting it fails when:

- the source run is one of production's own (`400`) or of another data source (`404`);
- the source run didn't end `COMPLETED`, or a view in production's scope didn't publish in it as
  `created`, `updated`, or `unchanged` with no `withheldMembers` (`409`);
- a newer build has succeeded since (`409`): publish it to staging and test it;
- Cube would convert other model files, or with another converter version, than the source run
  did (`409`), as after a Cube update or with Jinja that renders differently: publish to staging
  again. A converter change found only during conversion fails the run before it writes to
  Databricks.

A promotion can also get a temporary `409`, such as while a production run is active; a staging
run doesn't block it (see [Trigger publication from CI](#trigger-publication-from-ci)). Only the
message in the response body, which `--fail-with-body` prints, tells a temporary `409` from a
refusal, so read it before you retry.

A run returns its `targetName` and, when promoted, `promotedFromRunId`, which run history shows as
**Promoted from run**. Its `sourceSha256` hashes the model files it converted, and `runtime` names
the converter version it used.

### Publish to another workspace {#publish-to-another-workspace}

On a data source with a Databricks connection in its environment variables, a publication target
uses that connection unless it has one of its own, so one data source can publish to several
workspaces, such as staging to one and production to another. Create a
[service principal with an OAuth secret](https://docs.databricks.com/aws/en/dev-tools/auth/oauth-m2m)
for the other workspace and grant it the privileges listed in [Before you start](#before-you-start).
Then pick the target in the card, turn on **Use a separate connection** under
**Databricks connection**, enter the connection as in
[Data sources served by `driver_factory`](#data-sources-served-by-driver_factory), and save. That
target's Preview, Test access, and runs use this connection; targets without one, and your users'
queries, keep using the data source's.

A target with its own connection doesn't read `CUBEJS_DB_DATABRICKS_CATALOG`: if a cube uses a
two-part `schema.table` name, enter its **Default catalog**. To go back to the data source's
connection, turn **Use a separate connection** off and save, which removes the target's connection
and deletes its secret. Through the API, send `connection` as for a data source
[served by `driver_factory`](#data-sources-served-by-driver_factory).

## Check a pull request before it merges

A preview can convert YAML files sent with the request instead of the deployed model, so CI can
catch a change that breaks conversion before it reaches Databricks. Send `"source": "files"` and
`files`, a map of `.yml` or `.yaml` paths to their contents, such as your pull request's data model
folder: at most 512 files, 2 MiB each and 20 MiB in all, as for the deployed model. Paths are
relative to that folder, have no `.` or `..` segments, and use only letters, digits, `_`, `-`, `.`
and `/`. A preview of files is read-only like any other preview, has no `buildJobId` in its
response, and cannot be synced.

To find regressions, preview the pull request's files and the deployment, then compare the two
results view by view. A view regressed when it converts in the deployment but no longer converts
in the pull request (`eligibleForPublication` turned `false`), or when its `withheldMembers` gained
a measure. A view the pull request removes isn't compared.

Files sent with the request aren't rendered, so a file with [Jinja templates](#jinja-templates)
fails the preview with `400`, and the step below stops on a `.yml.jinja` or `.yaml.jinja` file.
Preview such a data model after it's deployed.

This Bash step requires `curl` 7.76 and `jq` 1.6 or later. Set `CUBE_API_URL` to your tenant host
without a trailing slash, `DEPLOYMENT_ID` to the production deployment, `CUBE_API_TOKEN` to a
[Platform API key](/api-reference/authentication) with deployment `SchemaRead` access, and
`MODEL_DIR` to the data model folder in your checkout. The example previews every view in the
model for the `default` data source; past 128 views, send the saved scope instead. Send the same
selection in both previews. To preview a deployed data model with Jinja templates, the key also
needs `SqlRunnerRead`. Set `MAX_POLLS` to scale the wait
for your view count and warehouse start-up time (default: 60 attempts per preview, 10 seconds
apart, plus request time). Starting a preview returns `429` with a `Retry-After` header while
Cube's preview capacity is exhausted; run the step again after that many seconds.

```bash
set -euo pipefail

previews="$CUBE_API_URL/api/v1/deployments/$DEPLOYMENT_ID/databricks-metric-view-previews"
auth_header="Authorization: Bearer $CUBE_API_TOKEN"
selection='{"dataSourceName": "default", "selectionMode": "all"}'
MODEL_DIR=${MODEL_DIR%/}
max_polls=${MAX_POLLS:-60}
[[ "$max_polls" =~ ^[1-9][0-9]*$ ]] || { echo 'MAX_POLLS must be a positive integer.' >&2; exit 1; }
results=$(mktemp -d)
trap 'rm -rf "$results"' EXIT

# Prints the completed result of the preview the request body on stdin starts.
preview() {
  local start status_url result_url status=''
  start=$(curl --fail-with-body --silent --show-error --connect-timeout 10 --max-time 60 -X POST \
    -H "$auth_header" -H 'Content-Type: application/json' --data-binary @- "$previews") ||
    { echo "$start" >&2; return 1; }
  status_url=$(jq -r '.statusUrl' <<<"$start")
  result_url=$(jq -r '.resultUrl' <<<"$start")
  for ((attempt=0; attempt<max_polls; attempt++)); do
    status=$(curl --fail --silent --show-error --connect-timeout 10 --max-time 30 \
      --retry 3 --retry-delay 5 -H "$auth_header" "$CUBE_API_URL$status_url")
    case "$(jq -r '.status' <<<"$status")" in
      QUEUED|RUNNING) sleep 10 ;;
      COMPLETED) jq -e '.resultAvailable' <<<"$status" >/dev/null && break; sleep 5 ;;
      *) jq '{status, error}' <<<"$status" >&2; return 1 ;;
    esac
  done
  if ! jq -e '.status == "COMPLETED" and .resultAvailable' <<<"$status" >/dev/null; then
    echo "The preview didn't finish within $max_polls polls; raise MAX_POLLS." >&2
    return 1
  fi
  curl --fail --silent --show-error --connect-timeout 10 --max-time 60 \
    --retry 3 --retry-delay 5 -H "$auth_header" "$CUBE_API_URL$result_url"
}

jinja=$(find "$MODEL_DIR" -type f \( -name '*.yml.jinja' -o -name '*.yaml.jinja' \) -print -quit)
[[ -z "$jinja" ]] || { echo "$jinja has Jinja templates; preview after deploying." >&2; exit 1; }

# Previews write to files, not $(...), so set -e stops the step when a request fails.
preview <<<"$selection" >"$results/deployed.json"
find "$MODEL_DIR" -type f \( -name '*.yml' -o -name '*.yaml' \) -print0 |
  while IFS= read -r -d '' file; do
    jq -n --arg path "${file#"$MODEL_DIR"/}" --rawfile content "$file" \
      '{key: $path, value: $content}'
  done |
  jq -s --argjson selection "$selection" '$selection + {source: "files", files: from_entries}' |
  preview >"$results/proposed.json"

regressions=$(jq -n '
  def members: [.withheldMembers[] | "\(.cube).\(.member)"];
  input as $deployed | input as $proposed
  | ($proposed.views | map({key: .cubeViewName, value: .}) | from_entries) as $after
  | [$deployed.views[] | select(.eligibleForPublication) | . as $before
      | $after[.cubeViewName] | select(. != null)
      | if .eligibleForPublication | not then
          {view: .cubeViewName, regression: "no longer converts",
           issues: [.issues[] | select(.severity == "ERROR") | .message]}
        elif (members - ($before | members)) != [] then
          {view: .cubeViewName, regression: "newly withheld",
           members: (members - ($before | members))}
        else empty end]' "$results/deployed.json" "$results/proposed.json")

if [[ "$regressions" != '[]' ]]; then
  jq . <<<"$regressions" >&2
  exit 1
fi
```

## What can be published

The **Preview** result is the authority for your deployed model. This preview release supports
YAML models, [Jinja-templated](#jinja-templates) ones included, `extends` between YAML cubes,
one Databricks data source per published view, scalar dimensions, common aggregates and supported
calculated measures, and many-to-one and one-to-one joins. Beyond that:

- **Joins:** a join condition that is not a plain column equality, such as an SCD2 date range, an
  expression like `CAST(...)` or `date_trunc(...)`, or a comparison with a literal, is published
  as written in the Metric View join's `on`, as long as it reads a column of the joined cube. A
  Metric View join keeps at most one match per source row: if the condition matches several rows
  of the joined cube, the Metric View keeps one of them where Cube keeps all, and Preview does not
  flag it. Make sure such a condition matches one row. A condition that compares the joined cube
  with another cube joined from the same cube, such as `{accounts}.plan = {plans}.plan_name` on the
  `deals` → `plans` join, is published with `plans` nested under `accounts`
  (`accounts.plans.list_price`) when both joins are many-to-one or one-to-one and the condition
  reads no column of `deals`. A view that also reaches `plans` another way is blocked, and Preview
  names both paths.
- **Dimensions:** a dimension can read a cube joined through many-to-one or one-to-one joins, such
  as `sql: "{users.name}"` on `orders`, a `{users}.name` column, or `coalesce({users.score}, 0)`.
  It is published through its join path, as `users.name`, or `a.b.column` for nested joins.
- **Measures:** a measure can read a joined cube through a join path from its own cube, such as
  `{CUBE.users.tier}` on `orders`, and is published with that cube joined along the path. Measure
  SQL can contain a subquery, such as
  `{CUBE}.id IN (SELECT order_id FROM returns WHERE returned_on = {CUBE}.created_at)` or a
  `GROUP BY ... HAVING` subquery.
- **Cube `sql`:** a cube's `sql` can read another cube's SQL with `{other_cube.sql()}`: it is
  expanded as Cube compiles it, so the published `source` is plain SQL.

The target uses Databricks Metric View YAML 1.1.

These categories reflect the current preview release. Capabilities may change between releases, so
run a new **Preview** after a Cube upgrade.

- **Supported** — a view with a clear root source and representable dimensions, measures,
  and joins. Review the generated YAML, then test access and sync.
- **Warning** — behavior-neutral metadata Databricks cannot represent, or a measure
  [withheld](#withheld-measures) as [`CUBE_MEMBER_WITHHELD`](#cube-member-withheld): a
  fan-out-unsafe joined measure, or a multi-stage or `rolling_window` measure a Metric View cannot
  represent. Review
  the exact difference before accepting publication.

Preview **blocks** a view it can't publish faithfully, and each blocking issue says what to
change in the model. [Fix a blocked view](#fix-a-blocked-view) has a section for each issue
code, with a before-and-after example.

### Withheld measures

A view's joins are the joins on its join path plus any joins that member SQL reaches, such as
`{CUBE.users.country}`. That includes the SQL of a member the view doesn't list but one of its
members references. A one-to-many join on the join path blocks the view, and so does a dimension
that reads a cube behind one
([`CUBE_VIEW_JOIN_NOT_REPRESENTABLE`](#cube-view-join-not-representable)). Otherwise, a
one-to-many join that member SQL reaches doesn't block the view, but it can withhold some of the
view's measures.

A measure of the view's root cube that reads a joined cube, such as
`SUM(CASE WHEN {products.family} = 'CX' THEN {CUBE}.events END)`, publishes when all of the
view's joins are many-to-one or one-to-one and the view has no root-source override: such joins
can't repeat a row of the root cube, so each row counts once, as in Cube.

A measure that can over-count is withheld: a non-idempotent aggregate, such as `sum`, `avg`, or a
`count` of an expression, or a calculated measure built on one. It is withheld in these cases:

- A measure of a joined cube: publish it from a view rooted at its own cube.
- A calculated measure that references another cube's measure: keep that view in Cube.
- A root-cube measure that reads a joined cube, in a view where member SQL reaches a one-to-many
  join, or in a view with a root-source override: remove the member reference that reaches that
  join, or the override, or keep that view in Cube.

A [multi-stage](/reference/data-modeling/measures#multi_stage) measure that a Metric View cannot
represent is withheld too: one with [`time_shift`](/reference/data-modeling/measures#time_shift),
[`grain`](/reference/data-modeling/measures#grain), `group_by`, `reduce_by`, or `add_group_by`, or
one of a type other than `number`, such as `rank`. So is a
[`rolling_window`](/reference/data-modeling/measures#rolling_window) measure, and any measure that
references one of these. These measures stay queryable in Cube. For a `time_shift` measure, you
can compute the prior period in Databricks with a window function, such as `LAG`, over `MEASURE()`
results. A view left with no measure to publish is blocked instead, as
[`CUBE_VIEW_FULLY_WITHHELD`](#cube-view-fully-withheld) or, when it also includes a dimension, as
`OSSIE_CUBE_MULTI_STAGE_MEASURE_PARKED` under [Fix a blocked view](#fix-a-blocked-view).

Preview lists each withheld measure, with its reason, under **Measures not published** and as a
`CUBE_MEMBER_WITHHELD` warning. In the Preview result, each entry in `withheldMembers` names the
member and its code:
`FANOUT_UNSAFE_METRIC` for a measure that would over-count, `MULTI_STAGE_UNSUPPORTED` for a
multi-stage or `rolling_window` measure. In a sync run, `withheldMembers` lists only the members,
as `cube.member`.

A view with a withheld measure is **still published without it**. That view may show
**Created**, **Updated**, or **Unchanged**, and the run may show **Completed**, even though some
measures are missing in Databricks. Check **Measures not published** in Preview and beside each
view in run history before treating a run as complete. Such a view counts toward the run's
`incompleteViewCount`. There is no opt-in gate for incomplete publication yet.

### References and subqueries in SQL

Preview publishes these as Cube compiles them, within the limits each one lists:

- A cube `sql` that reads another cube's SQL, such as `SELECT * FROM {orders_base.sql()}`,
  publishes with that SQL expanded, so the Metric View `source` is plain SQL. Preview blocks a
  reference that forms a cycle, names a cube outside the YAML model, goes through a join path
  (`{orders.users.sql()}`), or reads a cube whose own `sql` holds any other Cube reference, such
  as `{CUBE}` or a member.
- A member reference through a join path from the cube that holds the reference, such as
  `{CUBE.users.tier}` in an `orders` member, publishes as `users.tier`, joined along that path.
  Preview blocks the view if its own `join_path` entries reach that cube another way, since a
  Metric View joins each cube once.
  A plain `{users.tier}` names no path, so `users` needs exactly one join path from the view's
  root, or a view `join_path` entry that picks one (`includes: []` is enough).
- A measure's `sql` or `filters` can contain a subquery, such as this filter:
  `{CUBE}.account_id IN (SELECT account_id FROM raw.usage WHERE metric_ts = {CUBE}.metric_ts)`.
  Databricks doesn't resolve `source` columns inside a subquery, so each outer column it reads is
  added to the Metric View `source` under a generated name, such as `__cube_outer_0__`. Preview
  blocks a subquery that reads a joined cube, a measure, or a dimension whose SQL has a column
  without a `{CUBE}.` prefix. A subquery in dimension or join SQL is blocked too.

### Jinja templates

Preview and sync render [Jinja-templated](/docs/data-modeling/dynamic/jinja) YAML
files (`.yml`, `.yaml`, `.yml.jinja`, or `.yaml.jinja`) in the deployment, as Cube compiles
them, before converting the views. A file that only defines macros is left out. Rendering
requires all of these:

- You have **Access SQL Runner** (`SqlRunnerRead`)
  [access](/admin/users-and-permissions/custom-roles) to the deployment.
- The deployment runs Cube v1.3.11 or later.
- The request does not come from an embedded analytics session.

Otherwise, a preview or sync of a data model with Jinja templates fails with `400`, and the message
says what rendering needs.

Templates render with the deployment's default context, so Jinja that branches on the security
context or `COMPILE_CONTEXT` publishes only one variant. A braced `{COMPILE_CONTEXT…}` or other
[context variable](#cube-context-in-sql) left in a cube's `sql` blocks the view.

If a file fails to render, the preview or sync fails with `400` and names the file. A rendered file
can be up to 2 MiB, the rendered data model up to 20 MiB, and rendering can take up to 2 minutes.

For a few minutes after a build succeeds, the deployment's Cube runtime can still serve the
previous build while it rolls out the new one. Until the rollout finishes, starting a preview or
sync that renders templates fails with `409` and names both builds, so that a view is never
converted from a mix of the two. Try again once the rollout finishes.

## Fix a blocked view

Each issue in **Preview** names its code, the view, cube or member it applies to, and ends with
the change that fixes it. An issue whose code starts with `CUBE_` has a **How to fix** link to its
section below. Other codes come from the converters, and two of them block a view only when none
of its measures can publish: for `OSSIE_CUBE_FANOUT_UNSAFE_METRIC`, fix a measure as described
under [Withheld measures](#withheld-measures); for `OSSIE_CUBE_MULTI_STAGE_MEASURE_PARKED`, include
a measure that publishes, or keep the view in Cube. If any other converter code, such as `DBX_*`
or `DATABRICKS_CONVERTER_WARNING`, blocks a view, contact the
[Cube support team](/admin/account-billing/support).

### `CUBE_VIEW_NOT_FOUND` {#cube-view-not-found}

The selected view isn't in the deployed YAML model. Preview reads YAML only, so a view defined in
JavaScript or TypeScript is not found. Define the view in YAML, or select a view the model defines.

<CodeGroup>

```javascript title="Before (model/views/sales.js)"
view(`sales`, {
  cubes: [{ join_path: orders, includes: [`status`, `count`] }]
});
```

```yaml title="After (model/views/sales.yml)"
views:
  - name: sales
    cubes:
      - join_path: orders
        includes: [status, count]
```

</CodeGroup>

### `CUBE_VIEW_INVALID` {#cube-view-invalid}

The view's definition is malformed: a `cubes` entry without `join_path`, a `join_path` step whose
cube declares no join to the next one, `includes` or `excludes` that aren't lists, an empty
`alias`, a member that doesn't exist, or a dotted path in `includes`.
Correct the entry the issue names. A member of a joined cube is included from its own `cubes` entry.

<CodeGroup>

```yaml title="Before"
views:
  - name: sales
    cubes:
      - join_path: orders
        includes: [status, users.city]
```

```yaml title="After"
views:
  - name: sales
    cubes:
      - join_path: orders
        includes: [status]
      - join_path: orders.users
        includes: [city]
```

</CodeGroup>

### `CUBE_MODEL_INVALID` {#cube-model-invalid}

A cube definition can't be read: a reference to a member that doesn't exist, a reference cycle,
two joins to the same cube, a malformed `case`, or a malformed multi-stage property. A context
variable in a member's SQL, such as `{SECURITY_CONTEXT.region}`, reads as an unknown cube here.
Correct the cube or member the issue names, and remove any context variable from member SQL.

<CodeGroup>

```yaml title="Before"
measures:
  - name: avg_order
    sql: "{revenu} / {count}"
    type: number
```

```yaml title="After"
measures:
  - name: avg_order
    sql: "{revenue} / {count}"
    type: number
```

</CodeGroup>

### `CUBE_DUPLICATE_CUBE` {#cube-duplicate-cube}

Two files define a cube with the same name, so Preview can't tell which one a view reads. Keep one
definition, or rename one of them.

<CodeGroup>

```yaml title="Before (model/cubes/orders_v2.yml)"
cubes:
  - name: orders
    sql_table: main.sales.orders_v2
```

```yaml title="After (model/cubes/orders_v2.yml)"
cubes:
  - name: orders_v2
    sql_table: main.sales.orders_v2
```

</CodeGroup>

### `CUBE_DUPLICATE_VIEW` {#cube-duplicate-view}

Two files define a view with the same name. Keep one definition, or rename one of them, as for
[`CUBE_DUPLICATE_CUBE`](#cube-duplicate-cube).

### `CUBE_REFERENCED_CUBE_NOT_FOUND` {#cube-referenced-cube-not-found}

The view's `join_path` names a cube the model doesn't define. Define that cube, or remove it from
the view.

<CodeGroup>

```yaml title="Before"
views:
  - name: sales
    cubes:
      - join_path: orders.customer
        includes: [city]
```

```yaml title="After"
views:
  - name: sales
    cubes:
      - join_path: orders.customers
        includes: [city]
```

</CodeGroup>

### `CUBE_EXTENDS_UNSUPPORTED` {#cube-extends-unsupported}

The view `extends` another view, or a cube the view reaches extends a cube outside the YAML model,
such as a JavaScript cube. A Metric View would miss the members and access policy the view or cube
inherits. Define the view's cubes in the view itself, and extend only YAML cubes.

<CodeGroup>

```yaml title="Before"
views:
  - name: sales_eu
    extends: sales
    cubes:
      - join_path: orders.regions
        includes: [name]
```

```yaml title="After"
views:
  - name: sales_eu
    cubes:
      - join_path: orders
        includes: [status, count]
      - join_path: orders.regions
        includes: [name]
```

</CodeGroup>

### `CUBE_ACCESS_POLICY_UNSUPPORTED` {#cube-access-policy-unsupported}

The view, or a cube it reaches, has an `access_policy`, including one a cube inherits through
`extends`. A Metric View can't reproduce Cube's row and member policies, so publishing it would
bypass them. Keep that governed view in Cube. To publish the same data, add a view without
`access_policy`, over cubes without one, and control who can query its Metric View with Unity
Catalog grants.

<CodeGroup>

```yaml title="Before"
views:
  - name: sales
    access_policy:
      - group: analysts
        row_level:
          filters:
            - member: region
              operator: equals
              values: ["{ userAttributes.region }"]
    cubes:
      - join_path: orders
        includes: [region, count]
```

```yaml title="After"
views:
  # `sales` keeps its access_policy and stays in Cube.
  # This view is published; Unity Catalog grants control access to it.
  - name: sales_all_regions
    cubes:
      - join_path: orders
        includes: [region, count]
```

</CodeGroup>

### `CUBE_CONTEXT_IN_SQL` {#cube-context-in-sql}

A cube's `sql` reads a [context variable](/reference/data-modeling/context-variables), such as
`{FILTER_PARAMS…}`, `{SECURITY_CONTEXT…}`, or `{COMPILE_CONTEXT…}`. Only Cube can fill these in, so
Databricks can't run that SQL. Remove the variable from the cube's `sql`, or keep the view in Cube.
A context variable in a member's SQL is reported as
[`CUBE_MODEL_INVALID`](#cube-model-invalid), and in a join condition as
[`CUBE_VIEW_JOIN_NOT_REPRESENTABLE`](#cube-view-join-not-representable); remove it there too.

<CodeGroup>

```yaml title="Before"
cubes:
  - name: events
    sql: >
      SELECT * FROM main.app.events
      WHERE {FILTER_PARAMS.events.created_at.filter('created_at')}
```

```yaml title="After"
cubes:
  - name: events
    sql_table: main.app.events
```

</CodeGroup>

### `CUBE_MULTIPLE_DATA_SOURCES` {#cube-multiple-data-sources}

The cubes the view reads, including a cube that only a member's SQL references, use more than one
data source, and a Metric View reads one Databricks data source. Publish views whose cubes, and the
cubes their members read, all use the target's data source.

### `CUBE_DATA_SOURCE_MISMATCH` {#cube-data-source-mismatch}

A cube in the view uses a data source other than the publication target's. Leave that cube out of
the view, publish the view from a target on the cube's data source, or set the cube's
`data_source` to the target's.

<CodeGroup>

```yaml title="Before"
views:
  - name: sales
    cubes:
      - join_path: orders         # data_source: default
        includes: [count]
      - join_path: orders.leads   # data_source: crm
        includes: [source]
```

```yaml title="After"
views:
  - name: sales
    cubes:
      - join_path: orders
        includes: [count]
```

</CodeGroup>

### `CUBE_SOURCE_UNSUPPORTED` {#cube-source-unsupported}

A cube's `sql_table` or `sql` isn't a static Databricks table name or a plain `SELECT`: it has an
empty or extra name part, a two-part `schema.table` name with no default catalog, or a
`{other_cube.sql()}` reference through a join path. Write `sql_table` as `catalog.schema.table`.
For a two-part name, you can instead set `CUBEJS_DB_DATABRICKS_CATALOG` for the Databricks data
source, or the **Default catalog** of a publication target with its own connection.

<CodeGroup>

```yaml title="Before"
cubes:
  - name: orders
    sql_table: sales.orders
```

```yaml title="After"
cubes:
  - name: orders
    sql_table: main.sales.orders
```

</CodeGroup>

### `CUBE_VIEW_JOIN_PATH_UNSUPPORTED` {#cube-view-join-path-unsupported}

A Metric View has one source and joins each cube once, along one path. The view starts its
`join_path` entries at more than one cube, reaches a cube along two paths, has a cyclic path, or
its members read a cube along a path its joins don't follow. Start every `join_path` at the same
cube. When two of the view's own entries reach one cube, keep one of the paths. When members reach
a cube that several declared joins lead to, add an explicit `join_path` entry for it
(`includes: []` is enough).

<CodeGroup>

```yaml title="Before"
views:
  - name: deals_by_owner
    cubes:
      - join_path: deals
        includes: [amount]
      - join_path: employees
        includes: [name]
```

```yaml title="After"
views:
  - name: deals_by_owner
    cubes:
      - join_path: deals
        includes: [amount]
      - join_path: deals.employees
        includes: [name]
```

</CodeGroup>

### `CUBE_VIEW_JOIN_NOT_REPRESENTABLE` {#cube-view-join-not-representable}

A Metric View join keeps at most one row of the joined cube for each source row. These joins have
no such form, and the issue names the join:

- A `one_to_many` join on the view's join path, or a dimension that reads a cube behind one: root
  the view at the many-side cube.
- A join whose condition reads no column of the joined cube, such as `1 = 1` or
  `{CUBE}.status = 'open'`, including a cube the view reaches only through member SQL: Cube keeps
  every row it matches. Add a condition on a column of the joined cube, such as `{settings}.id = 1`
  for a single-row cube, or leave that cube and the members that read it out of the view.
- A join condition that reads a measure, or a cube other than the two it joins, including a
  `table.column` whose table is neither (except a join nested as described under
  [What can be published](#what-can-be-published)), or a context variable such as
  `{SECURITY_CONTEXT…}`, which reads as another cube: rewrite the condition on columns of the two
  cubes.

<CodeGroup>

```yaml title="Before"
joins:
  - name: layout
    sql: "1 = 1"
    relationship: many_to_one
```

```yaml title="After"
joins:
  - name: layout
    sql: "{CUBE}.layout_id = {layout}.id"
    relationship: many_to_one
```

</CodeGroup>

### `CUBE_MEMBER_UNSUPPORTED` {#cube-member-unsupported}

The view includes a member with no Metric View form: a segment, a hierarchy, a `geo` or `switch`
dimension, a `sub_query` dimension, a dimension that references a measure, or a time dimension
with custom `granularities`. Leave it out of the view with `excludes`, or drop it from `includes`.
For a time dimension with custom granularities, include a dimension with the same `sql` and no
`granularities` instead.

<CodeGroup>

```yaml title="Before"
cubes:
  - name: usage
    dimensions:
      - name: created_at
        sql: created_at
        type: time
        granularities:
          - name: fiscal_year
            interval: 1 year
            offset: 3 months
    segments:
      - name: paid_only
        sql: "{CUBE}.plan = 'paid'"

views:
  - name: usage_view
    cubes:
      - join_path: usage
        includes: "*"
```

```yaml title="After"
cubes:
  - name: usage
    dimensions:
      - name: created_at
        sql: created_at
        type: time
        granularities:
          - name: fiscal_year
            interval: 1 year
            offset: 3 months
      - name: created_at_time
        sql: created_at
        type: time
    segments:
      - name: paid_only
        sql: "{CUBE}.plan = 'paid'"

views:
  - name: usage_view
    cubes:
      - join_path: usage
        includes: "*"
        excludes: [created_at, paid_only]
```

</CodeGroup>

### `CUBE_MEMBER_SQL_UNSUPPORTED` {#cube-member-sql-unsupported}

A member's SQL has no Metric View form. The issue names the member and the case:

- A dimension with a subquery or a lambda: compute it in the cube's `sql` and read the result as a
  column.
- An aggregate of a measure that itself aggregates, such as a `count_distinct` of
  `{users.score_max}`: aggregate a dimension instead, such as `{CUBE.users.score}`.
- A measure that reads a column outside any aggregate, such as
  `CASE WHEN {layout.idx} = 1 THEN {count} END`: move the condition inside the aggregate.
- A measure subquery that reads a joined cube, a measure, or a dimension with a column not written
  as `{CUBE}.column`: select from the joined cube's table inside the subquery, and write such
  columns as `{CUBE}.column`.
- A dimension that reads a joined cube's columns or dimensions in a way the Metric View can't
  qualify: define it in the cube whose columns it reads.
- SQL that doesn't parse as Databricks SQL: rewrite it in Databricks SQL.

<CodeGroup>

```yaml title="Before"
cubes:
  - name: accounts
    sql_table: main.crm.accounts
    dimensions:
      - name: product_count
        sql: >
          (SELECT count(*) FROM main.crm.entitlements e
           WHERE e.account_id = {CUBE}.id)
        type: number
```

```yaml title="After"
cubes:
  - name: accounts
    sql: >
      SELECT a.*, e.product_count
      FROM main.crm.accounts a
      LEFT JOIN (
        SELECT account_id, count(*) AS product_count
        FROM main.crm.entitlements
        GROUP BY account_id
      ) e ON e.account_id = a.id
    dimensions:
      - name: product_count
        sql: product_count
        type: number
```

</CodeGroup>

### `CUBE_MEMBER_NAME_CONFLICT` {#cube-member-name-conflict}

Databricks compares names case-insensitively, and a Metric View dimension reads earlier dimensions
by name. Two published names in the view differ only in case, two joined cubes or a cube and the
reserved `source` alias collide, or two dimensions read each other's names where one of them is
published as `source` or with a join's name. Rename one of the members in the view with `alias` or
`prefix`: the published name is what collides. A joined cube whose name collides with another
join, or with `source`, must be renamed in the model: a view alias doesn't change the join's name.

<CodeGroup>

```yaml title="Before"
views:
  - name: sales
    cubes:
      - join_path: orders
        includes: [Status, count]
      - join_path: orders.users
        includes: [status]
```

```yaml title="After"
views:
  - name: sales
    cubes:
      - join_path: orders
        includes: [Status, count]
      - join_path: orders.users
        includes:
          - name: status
            alias: user_status
```

</CodeGroup>

### `CUBE_PRIMARY_KEY_REQUIRED` {#cube-primary-key-required}

A bare `type: count` measure counts rows of its cube, and the conversion needs the cube's primary
key to count them correctly through joins. Mark the key dimension with `primary_key: true`.

<CodeGroup>

```yaml title="Before"
dimensions:
  - name: id
    sql: id
    type: number
measures:
  - name: count
    type: count
```

```yaml title="After"
dimensions:
  - name: id
    sql: id
    type: number
    primary_key: true
measures:
  - name: count
    type: count
```

</CodeGroup>

### `CUBE_VIEW_FULLY_WITHHELD` {#cube-view-fully-withheld}

Every member the view includes is a measure with no Metric View form, such as a multi-stage,
`rolling_window`, or ranking measure, so a Metric View would have nothing to query. The message
lists each one. Include a measure that publishes, or keep the view in Cube. A view that also
includes a dimension is blocked as `OSSIE_CUBE_MULTI_STAGE_MEASURE_PARKED` instead, as described
under [Fix a blocked view](#fix-a-blocked-view).

### `CUBE_MEMBER_WITHHELD` {#cube-member-withheld}

A warning: the view publishes without a measure that would over-count, or that has no Metric View
form, such as a multi-stage, `rolling_window`, or ranking measure. The measure stays queryable in Cube. For
an over-counting measure, apply the fix for its case under [Withheld measures](#withheld-measures);
otherwise, keep that measure in Cube.

### `CUBE_PRESENTATION_METADATA_IGNORED` {#cube-presentation-metadata-ignored}

A warning: Databricks has no place for presentation settings, such as `format`, `currency`,
`drill_members`, `meta`, `folders`, or `view_groups`, so they aren't published. Query results don't
change, and nothing in the model needs to change.

### `CUBE_EXECUTION_METADATA_IGNORED` {#cube-execution-metadata-ignored}

A warning: `pre_aggregations` and `refresh_key` control how Cube runs queries, and a Metric View
queries the source tables directly, so they aren't published. Query results don't change, and
nothing in the model needs to change.

### `CUBE_PROJECTED_DATASET_UNKNOWN` {#cube-projected-dataset-unknown}

The conversion produced a dataset that matches no cube in the model. This is a converter
limitation, not a model error: contact the [Cube support team](/admin/account-billing/support)
and name the view.

### `CUBE_VIEW_PROJECTION_FAILED` {#cube-view-projection-failed}

The conversion refused the view for a reason without a specific code yet. Read the message: when it
names a model change, make it. For example, a `count` measure on a cube with no primary key is
reported here; fix it as described under
[`CUBE_PRIMARY_KEY_REQUIRED`](#cube-primary-key-required). Otherwise, contact the
[Cube support team](/admin/account-billing/support) and name the view.

## Ownership, failures, and rollback

Cube records ownership after a confirmed write. It refuses a view whose destination already
holds an object this publication target does not manage. Resolve the collision with the owner of the
Databricks object, by [taking over the destination](#take-over-an-existing-metric-view), or with
[Cube support](/admin/account-billing/support). Cube never deletes or overwrites an object it does
not manage unless you take over that exact destination. Cube does not compare a Metric View it
manages with its current definition in Databricks: a sync skips the view while its generated
definition is unchanged and otherwise replaces it, edits made in Databricks included. A Metric
View you drop in Databricks stays dropped until its generated definition changes, such as after a
change to the view or a cube it reads. A failed conversion, validation, or write leaves that view's
previous Databricks definition in place.
Other views in the same run may still publish.

You can request cancellation of an active run. It prevents further writes but does not undo
views already published. Saving the settings while a run is active, even to turn publication off,
fails that run before its next write. To roll back a bad definition, restore the desired Cube model and
deploy it. Then preview and sync again or, with [Publish after each deployment](#publish-after-each-deployment)
on, wait for that build's run to finish, then check that the card shows no
[Databricks is behind](#databricks-behind-the-deployed-model) warning, and select **Publish now**
if it does. Inspect run history and the Databricks target
afterward.
If publication is unavailable, contact [Cube support](/admin/account-billing/support) with
the deployment, data source, run ID, and each failed view's issue code, error class, and statement
ID. Do not send credentials or sensitive source data.

### Databricks behind the deployed model {#databricks-behind-the-deployed-model}

Databricks serves the Metric Views of the last build that a **Completed** or **Partial** run
published. When the deployment runs a newer build, the **Databricks Metric View sync** card shows
**Databricks is behind the deployed model**. The warning names the commit Databricks was last
published from and the commit the deployment runs. When both builds share a commit, as after a
redeploy, it names their build numbers instead. Select **Publish now** in the warning to publish
the deployed build; the warning clears once that run publishes it. A **Partial** run also
clears the warning, but its **Blocked**, **Rejected by Databricks**, and **Write failed** views
keep their earlier definitions, so check run history for them.

The warning doesn't show while publication is turned off, while a run is active, before the
first run publishes, or when the last run to publish predates build tracking. In that last case,
check run history to confirm a run published the deployed build. It can show briefly after a
deployment with [Publish after each deployment](#publish-after-each-deployment) on, until that run
starts.

Through the API, [reading the settings](/api-reference/databricks-metric-view-integration/get-databricks-metric-view-publication-settings)
returns `deployedBuild`, the deployment's newest successful build, and `publishedBuild`, the build
the newest **Completed** or **Partial** run converted. Each has a `buildJobId` and a `commit`.
`deployedBuild` is `null` when the deployment has no successful build. `publishedBuild` is `null`
until a run publishes, or when that run recorded no build, as a run from before these fields
existed does. When run history can't be read, the response leaves out `publishedBuild`.
Databricks is behind when both fields hold a build and their `buildJobId` values differ. The card
doesn't show the warning when either field is `null` or missing, so automation can apply the same
rule.

### Take over an existing Metric View

A sync labels a view **Blocked**, with one of these codes, when its destination already holds an
object this publication target does not manage:

- `unmanaged-target`: an object no publication in your Cube account manages, such as a Metric View
  made by hand, one your own pipeline writes to Databricks directly, or one a deleted
  [publication target](#publish-to-staging-then-production) left.
- `ownership-conflict`: another publication in your Cube account manages it: another
  [publication target](#publish-to-staging-then-production) of this data source, or another
  Databricks data source in this or another deployment.

To hand that destination to this publication target, take it over, which needs the same
`SchemaUpdate` access as any sync. The run replaces the object at that exact destination with the
view's Metric View and records it as managed by this publication target. The object's current
definition is lost. Later runs treat it like any other Metric View Cube manages. A publication
target that managed it before stops managing it, and its next sync reports that view **Blocked**
with `ownership-conflict`: remove the view from that target's scope or change where it publishes.
There is no option to take over everything: each take-over names its destinations, and without one
Cube overwrites nothing it does not manage.

- **In Console**: in the newest run in run history, select **Take over** next to the blocked view.
  The **Take over this destination?** confirmation names the destination; select
  **Take over destination**. This starts a sync with the saved settings that takes over only that
  destination. The run lists it under **Take-over requested**, and the view shows **Updated** with
  `taken-over`.
- **Through the API**: [start a run](/api-reference/databricks-metric-view-integration/start-a-databricks-metric-view-publication-run)
  with `takeOverTargets`, a list of destinations as `catalog.schema.name`, for example
  `{"configurationVersion": 12, "takeOverTargets": ["main.metrics.orders"]}`. Each must be exactly
  where a Cube view in the run's scope publishes, ignoring case; otherwise the start returns `400`
  and no run starts.

Databricks lets only a view's owner, or a principal with `MANAGE` on it, replace the view, and the
principal that replaces it becomes its owner (see
[`CREATE VIEW`](https://docs.databricks.com/aws/en/sql/language-manual/sql-ref-syntax-ddl-create-view)).
Before taking over an object, give the identity Cube publishes with ownership of it or `MANAGE` on
it; otherwise the view ends **Write failed** and the object keeps its definition. The replaced
object may not keep its Databricks grants, so check afterward that its consumers can still query
it.

A take-over runs alone in your Cube account. Starting one returns `409` while a run of another data
source or publication target is in flight, and starting such a run returns `409` while a take-over
is in flight. A run that ended `CANCELLED` or `FAILED` in the last 10 minutes counts as in flight,
because a write it sent may still land. A [deployment's run](#publish-after-each-deployment) retries
a `409` for about 30 minutes. The [CI recipe](#trigger-publication-from-ci) retries for about 5
minutes by default; if CI may start while a take-over runs, raise `MAX_START_ATTEMPTS`, for example
to 90 (about 15 minutes).

A failed take-over holds the run's drops, as a failed creation does (see
[Removed views](#removed-views)). Cancelling a take-over does not stop a write already sent to
Databricks. If that write lands, the new definition is live but Cube's record does not change: the
destination stays unmanaged, or stays managed by the other publication target, which skips it
while that view's model is unchanged and replaces it with its own definition once the model
changes. Run the take-over again to record it.

### Removed views

A Metric View becomes obsolete when its view leaves the scope (you deselect it, edit the pattern
so it no longer matches, or remove or rename it under **all** or **pattern**; a selected view you
remove or rename stays in scope, see the scope rules under [Publish a view](#publish-a-view)) or the
view's target name changes (a target-name override or prefix change). By default an obsolete
Metric View stays in Databricks, and run history labels it **Obsolete, kept**. To have syncs drop
obsolete Metric Views,
choose **Delete the Metric View Cube created** under **When a view leaves the scope**, or save
`deletionPolicy: delete-managed` through the API. The next sync drops each one and labels it
**Obsolete, deleted**. A dropped Metric View loses its Databricks grants; if its target comes back,
the next sync creates it again without them.

Cube drops a Metric View only when all of these hold:

- Cube created it and still records it as its own, in the catalog and schema its publication
  target publishes to now, in the same Unity Catalog metastore. After you change the target
  catalog or schema, the Metric Views in the old location stay in Databricks and every sync
  labels them **Obsolete, kept** without a `detail`, so CI still passes. Drop them in Databricks
  yourself; run history keeps listing them.
- It is obsolete: its Cube view left the scope, or the view now publishes to another target
  name. A view still in scope whose conversion or write failed keeps its Metric View.
- The object at that name is still a view, owned by the Databricks principal Cube publishes with.
  Cube checks this just before it drops it. If you transfer ownership of Cube's Metric Views,
  Cube no longer drops them: each sync labels such a Metric View **Obsolete, kept** with
  `precondition-failed`. Drop it in Databricks yourself, and the next sync labels it
  **Obsolete, deleted** and stops tracking it.

A sync drops nothing, and labels each Metric View it would have dropped **Obsolete, kept** with the
reason, when:

- `no-views`: no view in the sync converted to a Metric View definition;
- `create-failed`: a new view's Metric View or a
  [take-over](#take-over-an-existing-metric-view) wasn't written (Databricks rejected or failed it,
  or an object Cube doesn't manage holds its name: `unmanaged-target`), so a renamed view would
  otherwise lose both names;
- `deletion-cap-exceeded`: it would drop more than 20 Metric Views. Remove views in batches of
  at most 20 per sync. The hold repeats on every sync while more than 20 are obsolete, and
  dropping them in Databricks yourself does not clear it. Restore views or revert the target-name
  change until 20 or fewer are obsolete, or switch to **Keep its Metric View in Databricks**,
  which keeps them all.

A failed drop is labeled **Obsolete, kept** with its failure code, and the next sync tries again. A
data model file that fails to load stops the sync before anything is written or dropped. Disabling
publication, or Cube support deactivating the preview for your account, drops nothing. Dropping
needs the same Databricks privileges on the target schema as replacing a view.

### Move to another metastore

After you point the data source, or a publication target's own connection, at a workspace on
another Unity Catalog metastore, the next sync creates its Metric Views there, or labels a view
**Blocked** with `unmanaged-target` when an object there already holds its name; if that object
should belong to this publication target, [take it over](#take-over-an-existing-metric-view). The
Metric Views in the old metastore stay, and syncs no longer list them: drop them in Databricks
yourself.
