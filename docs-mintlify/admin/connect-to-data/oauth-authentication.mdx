---
title: Set up per-user OAuth
description: Configure Cube to authenticate each user with their own OAuth token, falling back to a service account when a user has no active token.
---

<Note>

This feature is in beta. Reach out to your account manager to have it
enabled for your Cube deployment.

</Note>

## Use case

You want each user's queries to run under their own database identity
using OAuth tokens managed by Cube. When a user has no active
token, for example because they haven't authorized yet, Cube falls back
to a service account, which also runs background operations such as
pre-aggregation builds.

This pattern applies to any data source that supports OAuth, including
[Databricks][ref-databricks-jdbc] and [Snowflake][ref-snowflake]. The
examples below use Databricks; for any other OAuth-capable data
source, update the driver options.

Because every user connects with different credentials, you also need
per-user query orchestrator state. Without this, one user's cached
connection could leak to another.

## Prerequisites

- A [Cube][ref-cube-cloud] deployment connected to an
  OAuth-capable data source
- OAuth configured in your data source so that Cube can
  obtain per-user tokens (via the **User Credentials** feature)
- A service account credential (token or password) stored as an
  environment variable, used for background operations and for users
  without an active token

<Warning>

The service account credential is used for background operations, such
as pre-aggregation builds, and for queries from users without an active
token, who see whatever the service account can access. Grant it the
minimum permissions necessary — ideally read-only access to the required
schemas — to limit exposure. To reject those queries instead, make
`driver_factory` fail closed for user requests and keep the service
account token only for the refresh worker's context, as in the
[per-user OIDC token example][ref-oidc-per-user]. Fail closed with a
non-empty token the warehouse rejects: an empty token makes the
Databricks and Snowflake drivers read a credential from the environment
instead.

Anyone who can sign tokens with the deployment's API secret can set
`cubeCloud.username` and query as that user, with that user's OAuth
token. Protect the API secret like your users' credentials.

</Warning>

## Set up the OAuth app

Before configuring Cube to use per-user OAuth, register your data
source as an OAuth app in Cube:

<Steps>

<Step title="Open the OAuth apps settings">

In Cube, go to **Admin → Integrations → OAuth apps** and click
**Create OAuth app**.

<Frame>
  <img src="https://static.cube.dev/docs/admin/connect-to-data/oauth-authentication/oauth-add-app.png" alt="Admin Integrations page showing the OAuth apps section with the Create OAuth app button" />
</Frame>

</Step>

<Step title="Fill out the OAuth app details">

Enter a **Name** for the OAuth app and pick a **Provider**: **Snowflake**
or **Databricks** fill in the OAuth endpoints and scopes for you, and
**Custom** works with any other OAuth provider. For Snowflake and
Databricks, the derived **Auth URL**, **Token URL** and **Scopes** are
shown as read-only fields, so you can see what Cube saves.

Copy the **Redirect URI** shown in the form; your data source needs it to
send users back to Cube after they authorize.

<Tabs>

<Tab title="Snowflake">

Enter the **Account identifier**, as `<org>-<account>`, or paste the
account URL; Cube strips the scheme and the `.snowflakecomputing.com`
suffix. Enter the **Role** that users connect with, exactly as it is named
in Snowflake, case included. Snowflake doesn't accept `ACCOUNTADMIN` or
other admin roles as the session role.

Cube derives:

| Field | Value |
|---|---|
| **Auth URL** | `https://<org>-<account>.snowflakecomputing.com/oauth/authorize` |
| **Token URL** | `https://<org>-<account>.snowflakecomputing.com/oauth/token-request` |
| **Scopes** | `refresh_token`, `session:role:<ROLE>` |

The `refresh_token` scope lets Cube refresh the access token, so users
don't have to authorize again each time it expires.

The form also shows the statements to run in Snowflake as `ACCOUNTADMIN`,
with the redirect URI filled in. Copy and run them: the first one creates
the security integration, and the second one returns the client ID and
client secret.

```sql
CREATE SECURITY INTEGRATION CUBE_<NAME>
  TYPE = OAUTH
  OAUTH_CLIENT = CUSTOM
  OAUTH_CLIENT_TYPE = 'CONFIDENTIAL'
  OAUTH_REDIRECT_URI = '<redirect-uri>'
  OAUTH_ISSUE_REFRESH_TOKENS = TRUE
  ENABLED = TRUE;

SELECT SYSTEM$SHOW_OAUTH_CLIENT_SECRETS('CUBE_<NAME>');
```

Users have to authorize again once their refresh token expires, after 90
days by default. To change that, add
`OAUTH_REFRESH_TOKEN_VALIDITY = <seconds>` to the
`CREATE SECURITY INTEGRATION` statement.

Enter the returned values as **Client ID** and **Client secret**.

  <img src="https://static.cube.dev/docs/admin/connect-to-data/oauth-authentication/oauth-app-form-snowflake-v2.png" alt="New OAuth app form with the Snowflake provider: Account identifier and Role fields, the Snowflake setup statements, and the derived Auth URL, Token URL, and Scopes" />
</Frame>

</Tab>

<Tab title="Databricks">

Enter the **Workspace URL**, for example
`https://dbc-XXXXXXX-XXXX.cloud.databricks.com`. Cube keeps only the
origin, so you can paste the URL from your browser as is.

Cube derives:

| Field | Value |
|---|---|
| **Auth URL** | `https://<workspace>/oidc/v1/authorize` |
| **Token URL** | `https://<workspace>/oidc/v1/token` |
| **Scopes** | `all-apis`, `offline_access` |

In your Databricks account, create an OAuth app connection with the
**Redirect URI** from the form, and enable the `all-apis` and
`offline_access` scopes on it. `offline_access` lets Cube refresh the
access token, so users don't have to authorize again each time it
expires. Set `token_access_policy.refresh_token_ttl_in_minutes` on the
app connection to how long a user can go before authorizing again.

Enter the app connection's client ID and secret as **Client ID** and
**Client secret**.

<Frame>
  <img src="https://static.cube.dev/docs/admin/connect-to-data/oauth-authentication/oauth-app-form-databricks-v2.png" alt="New OAuth app form with the Databricks provider: Workspace URL field and the derived Auth URL, Token URL, and Scopes" />
</Frame>

</Tab>

<Tab title="Custom">

Enter the **Auth URL**, **Token URL**, **Client ID** and **Client
secret** from your data source's OAuth provider, and any required
**Scopes**, comma-separated. Register the **Redirect URI** with the
provider.

Request a refresh token, if the provider supports it, so users don't
have to authorize again each time the access token expires.

</Tab>

</Tabs>

To keep idle users connected, turn on **Keep users signed in**. Cube
then renews each user's access token in the background, so it doesn't
expire while the user is away. This works only when the provider issues
a refresh token. The setting is off by default: Cube renews a token only
when it's used, and users who stay idle longer than the provider allows
have to authorize again.

Click **Create**.

</Step>

<Step title="Authorize the app">

Each user does this for their own account. An admin's token is
never used for other users.

Open the sidebar and go to **Connected accounts**. Find your OAuth app
and click **Authorize** to generate an access token.

Cube refreshes the access token automatically as long as the provider
issues a refresh token. A user needs to authorize again only if the
refresh token expires or is revoked; **Connected accounts** shows the
current status.

</Step>

## Configuration

The configuration uses two options from the
[configuration file reference][ref-config]:

- [`driver_factory`][ref-driver-factory] — dynamically selects the
  authentication credential per request
- [`context_to_orchestrator_id`][ref-context-to-orchestrator-id] — gives
  each user, and each of their tokens, a separate query orchestrator
  instance (database connections, execution queues, pre-aggregation table
  caches)

### Environment variables

Set the environment variables for your data source. The examples below
show Databricks and Snowflake; adapt them to your specific setup.

<Tabs>

<Tab title="Databricks">

```dotenv
CUBEJS_DB_TYPE=databricks-jdbc
CUBEJS_DB_DATABRICKS_URL=jdbc:databricks://dbc-XXXXXXX-XXXX.cloud.databricks.com:443/default;transportMode=http;ssl=1;httpPath=sql/protocolv1/o/XXXXX/XXXXX;AuthMech=3;UID=token
CUBEJS_DB_DATABRICKS_TOKEN=dapi_service_account_token
CUBEJS_DB_DATABRICKS_ACCEPT_POLICY=true
# Optional: specify a catalog
CUBEJS_DB_DATABRICKS_CATALOG=my_catalog
```

Use a token for the service account. If
`CUBEJS_DB_DATABRICKS_OAUTH_CLIENT_ID` is set, the driver authenticates as
that service principal and ignores the per-user `token`.

</Tab>

<Tab title="Snowflake">

```dotenv
CUBEJS_DB_TYPE=snowflake
CUBEJS_DB_SNOWFLAKE_ACCOUNT=XXXXXXXXX.us-east-1
CUBEJS_DB_SNOWFLAKE_WAREHOUSE=MY_SNOWFLAKE_WAREHOUSE
CUBEJS_DB_NAME=my_snowflake_database
CUBEJS_DB_USER=service_account_user
CUBEJS_DB_PASS=service_account_password
CUBEJS_DB_SNOWFLAKE_ROLE=MY_ROLE
```

</Tab>

</Tabs>

### Configuration file

The examples below use Databricks with an OAuth app named `databricks`.
`userCredentials` is keyed by the **Name** of the OAuth app, so replace
`databricks` with the name of your app. To target a different data
source, also update the `driver_factory` return value with the correct
`type` and driver-specific options. See the
[data sources reference][ref-data-sources] for available drivers.

<Tabs>

<Tab title="Python">

```python cube.py
from cube import config
import os


@config("driver_factory")
def driver_factory(ctx: dict) -> dict:
    # Extract the Cube security context, which contains
    # per-user OAuth credentials when available.
    # "databricks" is the Name of the OAuth app.
    databricks_creds = (
        ctx
        .get("securityContext", {})
        .get("cubeCloud", {})
        .get("userCredentials", {})
        .get("databricks", {})
    )

    # Only use the OAuth token when the credential status is "active".
    # Otherwise ("missing", "expired", or "error"), fall back to the
    # service account.
    oauth_token = (
        databricks_creds.get("accessToken")
        if databricks_creds.get("status") == "active"
        else None
    )

    return {
        "type": "databricks-jdbc",
        "url": os.environ["CUBEJS_DB_DATABRICKS_URL"],
        # Prefer the user's OAuth token; fall back to the service account token
        "token": oauth_token or os.environ["CUBEJS_DB_DATABRICKS_TOKEN"],
        "acceptPolicy": True,
        "catalog": os.environ.get("CUBEJS_DB_DATABRICKS_CATALOG"),
    }


@config("context_to_orchestrator_id")
def context_to_orchestrator_id(ctx: dict) -> str:
    # Give each user a separate orchestrator instance (DB connections,
    # execution queues, pre-aggregation caches). The driver is cached per
    # orchestrator, so the key also changes with the user's token.
    cube_cloud = ctx.get("securityContext", {}).get("cubeCloud", {})
    username = cube_cloud.get("username", "default")
    databricks_creds = cube_cloud.get("userCredentials", {}).get("databricks", {})
    token_key = (
        databricks_creds.get("issuedAt")
        if databricks_creds.get("status") == "active"
        else "fallback"
    )
    return f"CUBE_APP_{username}_{token_key}"
```

</Tab>

<Tab title="JavaScript">

```javascript cube.js
module.exports = {
  driverFactory: ({ securityContext }) => {
    // Extract the Cube security context, which contains
    // per-user OAuth credentials when available.
    // `databricks` is the Name of the OAuth app.
    const databricksCreds =
      securityContext?.cubeCloud?.userCredentials?.databricks ?? {};

    // Only use the OAuth token when the credential status is "active".
    // Otherwise ("missing", "expired", or "error"), fall back to the
    // service account.
    const oauthToken =
      databricksCreds.status === "active"
        ? databricksCreds.accessToken
        : null;

    return {
      type: "databricks-jdbc",
      url: process.env.CUBEJS_DB_DATABRICKS_URL,
      // Prefer the user's OAuth token; fall back to the service account token
      token: oauthToken || process.env.CUBEJS_DB_DATABRICKS_TOKEN,
      acceptPolicy: true,
      catalog: process.env.CUBEJS_DB_DATABRICKS_CATALOG,
    };
  },

  // Give each user a separate orchestrator instance (DB connections,
  // execution queues, pre-aggregation caches). The driver is cached per
  // orchestrator, so the key also changes with the user's token.
  contextToOrchestratorId: ({ securityContext }) => {
    const username = securityContext?.cubeCloud?.username ?? "default";
    const databricksCreds =
      securityContext?.cubeCloud?.userCredentials?.databricks ?? {};
    const tokenKey =
      databricksCreds.status === "active"
        ? databricksCreds.issuedAt
        : "fallback";
    return `CUBE_APP_${username}_${tokenKey}`;
  },
};
```

</Tab>

</Tabs>

For Snowflake, return `authenticator: "OAUTH"` with the user's token as
`oauthToken`. The Snowflake driver ignores a `token` option, so without
these two options it connects as the service account and reports no
error. Options that `driver_factory` doesn't return, such as the account,
warehouse and role, come from the environment variables. Set
`CUBEJS_DB_SNOWFLAKE_ROLE` to the **Role** of the OAuth app: Snowflake
rejects the connection when the role differs from the one in the token.
In `context_to_orchestrator_id`, read `issuedAt` from the same app's
credentials, here `userCredentials.snowflake`, so that a new token gets a
new driver.

```python cube.py
@config("driver_factory")
def driver_factory(ctx: dict) -> dict:
    # "snowflake" is the Name of the OAuth app
    snowflake_creds = (
        ctx
        .get("securityContext", {})
        .get("cubeCloud", {})
        .get("userCredentials", {})
        .get("snowflake", {})
    )

    if snowflake_creds.get("status") == "active":
        return {
            "type": "snowflake",
            "authenticator": "OAUTH",
            "oauthToken": snowflake_creds["accessToken"],
        }

    # Fall back to the service account
    return {"type": "snowflake"}
```

## How it works

1. **User makes a request** — Cube attaches the user's own OAuth
   credentials to `securityContext.cubeCloud.userCredentials.<app_name>`,
   where `<app_name>` is the **Name** of the OAuth app, as
   `{ status, accessToken, accessTokenExpiresAt, issuedAt, connectUrl }`.
   `issuedAt` changes whenever the token is replaced. `connectUrl` is the
   URL of the **Connected accounts** page, where the user authorizes or
   re-authorizes the app; use it to tell users how to fix a `missing` or
   `expired` credential. Requests that aren't tied to a
   Cube user carry no user credentials, so they also fall back to the
   service account. This includes requests authenticated with your own JWT
   or `checkAuth`, unless their security context sets
   `cubeCloud.username`.

2. **`driver_factory` resolves the credential** — If the credential status
   is `active`, the user's OAuth token is used. Otherwise — the user hasn't
   authorized (`missing`), or the token is `expired` or in `error` — Cube
   falls back to the service account credential stored in environment
   variables.

3. **Per-user orchestrator** —
   [`context_to_orchestrator_id`][ref-context-to-orchestrator-id] returns
   a unique key per username, so each user gets their own database
   connection pool, execution queues, and pre-aggregation table cache.
   Without this, Cube would share a single cached connection across all
   users, causing one user's credentials to be reused for another user's
   queries. Cube builds the driver once per orchestrator, so the key also
   includes the token's `issuedAt`: when a user authorizes or their token
   is refreshed, Cube builds a new connection with the current token. The
   trade-off: each refresh starts the user on a new orchestrator with an
   empty cache and new connections, and superseded orchestrators keep
   theirs, which the liveness probe keeps testing, until they are evicted
   from the orchestrator cache.

4. **Failed queries point to Connected accounts** — When a query fails
   with an error from the data source and any of the user's credentials
   is `missing`, `expired` or in `error`, Cube appends a hint to the
   error message. The hint names the OAuth app and links to
   **Connected accounts**, so a user who gets a permission error from the
   service account knows to connect or reconnect their account. SQL API
   and MCP clients show the hint as part of the message. The REST (JSON)
   API error response also includes `userCredentials`, with an entry for
   each such credential, so API clients can handle the case without
   parsing the message:

   ```json
   {
     "error": "<data source error>\n\nThis may be because you have not connected your databricks account to Cube. Connect it at https://example.cubecloud.dev/connected-accounts, then retry.",
     "requestId": "...",
     "userCredentials": [
       {
         "integration": "databricks",
         "status": "missing",
         "connectUrl": "https://example.cubecloud.dev/connected-accounts"
       }
     ]
   }
   ```

   Errors that Cube raises itself, such as authentication or validation
   errors, carry no hint, and status codes don't change.
